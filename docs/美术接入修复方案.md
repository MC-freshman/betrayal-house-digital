## 1. 问题陈述

### 1.1 现象

| 能力 | 现状 | 直接后果 |
| --- | --- | --- |

### 1.2 为什么既有 A 表没兜住

既有 34 项在设计上只覆盖"**素材本身**"和"**美术预览页**"，没有一条覆盖"**对局渲染**"：

| 项 | 断言对象 | 取样位置 | 对"对局是否用图"的判定力 |
| --- | --- | --- | --- |
| A-19 / A-20 / A-21 | 房间 128/160/192、卡牌 240×336/300×420/360×504 的物理像素 | `qa/ui_capture.py` 打开**帮助窗口 → 美术预览页签**，读 `dialog._art_photo` | 无。预览页画了图，对局可以是纯文字 |
| A-22 | 图形 ≥3:1、正文 ≥4.5:1 | `ui_capture.json` 的 `contrast_*`，方法为 `wcag-relative-luminance(ui.PALETTE design values)` | 无。只验色值与设计值 |
| A-32 | 母版/运行时尺寸、真 PNG、alpha、M-13 可读性、渲染层 WCAG | P 表 + `qa/run5_readability.json` + 100% 截图 | 无。规格合格 ≠ 被使用 |
| A-30 / A-31 | 台账 0 missing、130 张转码无损 | P 表 / 转码清单 | 无。登记与转码与 UI 无关 |
| A-08 | 运行时 PNG 计数 50/80/12/3 | 目录计数 | 无。文件存在 ≠ 被渲染 |

### 1.3 口径缺口的形式化

存在一组同时满足下列两件事的状态，而现行 A 表全 PASS：

1. P 表 142/142 `usable`、运行时 145 张、A-19…A-22、A-32 全 PASS；
2. 对局界面渲染图片数 = 0。

即：**现行验收体系对"美术是否接入"不可判定**。这不是数据缺陷，是验收口径不完备。

结论：**不改写任何既有项**，新增一项 **A-33 对局美术渲染**，与 A-32 并列归 G5，专门锁"对局渲染"这一层。

## 3. 每处实现契约

### 3.1 统一取图入口

```python
# ui.py（模块级）
ART_CACHE_CAPACITY   = 192      # 50 房间 + 80 卡 + 12 角色 + 余量
ART_LEDGER_CAPACITY  = 512      # 环形账本，供 A-33 只读取证
ART_REFS_MAX         = 256      # 显示中图片的强引用上限
ROOM_SIZE_LADDER     = (64, 96, 128, 192, 256, 384)     # 规范：房间图块 96/128
PORTRAIT_SIZE_LADDER = (64, 96, 160, 320)               # 规范：角色头像 160/320
CARD_FACE_BASE       = (240, 336)                       # 规范：卡牌 240×336（5:7）

# GameApp 方法（注意：不得叫 _art_photo —— 该名字已被 _HelpDialog 实例属性占用，
# 且被 qa/ui_capture.py 读取）
def _art_image(self, key, asset_type, size, surface):
    """四处接线唯一的取图入口；返回 PhotoImage 或 None。"""
```

**契约（缺一不可）**

1. `key` 必须是 P 表 `runtime_key` 或可被 `AssetRegistry.resolve` 反查的键（`content_ref` / 裸 id 亦可，但只允许 W-3 用裸 id）。
2. `size` 必须是 `_ladder_size(...)` 或 `_card_face_size()` 的结果，**不接受任意整数**（否则缓存键被打散）。
3. **占位检测前置**：`ref.path` 不存在时**不调用** `load_asset_photo`，直接记 `placeholder=True / reason="file-missing"` 并返回 `None`。
   理由：绑定层在文件缺失时会**返回占位图 PhotoImage 而不是 None**（`ui_asset_binding.py:236-260`），若把判定交给绑定层，"落到占位图"就不可机读。前置判定让 A-33 的"非占位"断言确定可判。
4. **记账无条件**：每次调用（成功/失败/命中/未命中）都追加一条账本记录，不设开关。禁止只在探针模式下记账——否则探针走的是另一条代码路径，证据不可信。
5. **引用分离**：LRU 缓存只负责"解码复用"；**显示中的 PhotoImage 必须另存强引用**（`self._art_refs`）。Tk 的 canvas item 只持有 Tk 内部 image 名，Python 对象一旦被回收，画布立即变空白——缓存淘汰导致的空白是本次最可能的线上事故。
6. 新开一局 / 读档时：`self._art_cache.clear()`、`self._art_refs.clear()`、账本清空。

**账本记录 schema**

```json
{
  "seq": 17,
  "surface": "board|card|panel|portrait|room_tooltip|room_detail",
  "key": "room:entrance_hall",
  "asset_type": "room",
  "requested": [96, 96],
  "actual": [96, 96],
  "record_id": "P-ROOM-004",
  "rel_path": "source/desktop/game/assets/rooms/entrance_hall.png",
  "placeholder": false,
  "reason": "",
  "cache": "hit|miss|error",
  "at": "2026-11-22T10:00:00"
}
```

`reason ∈ {"", "unresolved", "file-missing", "decode", "no-registry"}`；`placeholder=true` 只可能在 `file-missing` 时出现（见契约 3）。

### 3.2 尺寸推导

```python
def _effective_dpi(self) -> int:
    """复用 _HelpDialog._read_effective_dpi() 的读取口径（ctypes GetDeviceCaps）。"""

def _ladder_size(self, asset_type: str, logical_px: int):
    want = int(round(logical_px * self._effective_dpi() / 96.0))
    ladder = ROOM_SIZE_LADDER if asset_type == "room" else PORTRAIT_SIZE_LADDER
    best = max([v for v in ladder if v <= want] or [ladder[0]])
    return (best, best)

def _card_face_size(self):
    f = self._effective_dpi() / 96.0
    return (max(1, int(round(240 * f))), max(1, int(round(336 * f))))
```

设计理由：

- **为什么用阶梯**：`load_asset_photo` 的缓存键含 `max_size`（`ui_asset_binding.py:241-246`）。棋盘瓦片尺寸随窗口宽度与 `self.zoom` 连续变化，若直接传 `ts` 会把缓存打穿成"每次缩放全部重解码"。阶梯把取值收敛到 6 档。
- **为什么不复用 `_art_scaled_size`**：该方法是 `_HelpDialog` 按 DPI 整档缩放的预览页口径（96dpi→128/128、150dpi→192/192），被 A-19/20/21 直接断言。对局棋盘需要的是"贴合瓦片"的另一套口径，两者混用会让 A-19/20/21 的期望值随 UI 布局漂移。**唯一例外是卡面**：卡面刻意复用同一基准 `240×336`，使 W-2 与 A-19/20/21 同源，不引入第二套卡面公式。
- **DPI 换算**：PhotoImage 不随 Tk 缩放自动放大，故按 `dpi/96` 换算像素；否则 150% 缩放下棋盘图会明显偏小。

### 3.3 缓存策略

| 项 | 策略 |
| --- | --- |
| 实例 | `self._art_cache = ui_asset_binding.AssetImageCache(capacity=ART_CACHE_CAPACITY)`，每进程一份，绑定 `self`（master） |
| 键 | 由绑定层生成：`(record_id|target_ref, primary_path, max_size, id(master))` |
| 命中目标 | 同一次对局内重复重绘 100% 命中（棋盘每次 `_redraw_board` 都会重取 25~50 张） |
| 淘汰 | LRU；**淘汰不影响已显示图**（显示引用在 `_art_refs`） |
| 观测量 | `cache_stats(master)` 的 hits/misses/evictions/errors 写进探针，用于解释首帧耗时 |
| 失效 | 新局/读档/切换 `zoom` 档位跨阶梯时自然未命中；不手动 clear（除新局） |

### 3.4 W-1 棋盘房间贴图

```python
def _draw_room_art(self, canvas, room, px, py, ts, tag) -> bool:
    band_h = max(16, int(ts * 0.22))
    art_h  = max(8, ts - band_h)
    photo  = self._art_image("room:%s" % room.template_id, "room",
                             self._ladder_size("room", art_h), "board")
    if photo is None:
        return False                      # 缺图：保留 3.4 的底色矩形，纯文字兜底
    canvas.create_image(px + ts / 2, py + art_h / 2, anchor="center",
                        image=photo, tags=(tag, "room_art"))
    return True
```

- **绘制顺序**（`_redraw_board` 内每间房）：底色矩形（现状，保留）→ 房间图（新增，居中于上部 `art_h`）→ 底部名称带（新增，`PALETTE["panel3"]` 实心矩形，高 `band_h`）→ 房名文本（移入名称带）→ 楼层标签（移到名称带右端小字）→ 门标记（现状）。
- **对比度**：名称带 `#20252d` + 正文 `#eef2f6`，设计值约 12.6:1，与 A-22 现用色值为同一组 token，**不引入新色值**。
- **取图键**：`room:<room.template_id>`。`content.build_catalog().room_templates` 的 49 个 id 与 P 表 50 个 `runtime_key` 的差集为 `{storeroom}`（P 表有、content 无对应模板），故棋盘最多渲染 49 个不同房间；`storeroom` 属结构性不可达，由 A-33 J6 显式登记，不算缺陷。
- **缺图兜底**：`_draw_room_art` 返回 `False` → 该瓦片维持现状（色块 + 房名），不画空图、不画占位图；账本记 `placeholder=True`（仅当 `ref.path` 缺失）。
- **缓存**：尺寸阶梯 + 每局只解码一次。

### 3.5 W-2 抽卡弹窗卡面

```python
def _resolve_card_notice(self, title: str):
    """'抽到预兆：X' / '获得物品：X' / '触发事件：X' → (kind, card_id) 或 None。"""
    for prefix, kind in (("抽到预兆：", "omen"), ("获得物品：", "item"), ("触发事件：", "event")):
        if title.startswith(prefix):
            name = title[len(prefix):].strip()
            return self._card_index.get((kind, name))     # 懒建；冲突返回 None
    return None

class _CardDialog:
    def __init__(self, root, title, message, photo=None):
        ...
        self.photo = photo            # 强引用，防 GC
```

- **接线点**：`TkDecisionProvider.notify()`（`ui.py:152-155`）改为先试 `_resolve_card_notice`，命中则开 `_CardDialog`，否则维持 `_InfoDialog`。**`engine_parts/room_effects.py` 不改**——标题文本是既有契约（三处 `notify` 的前缀已核对）。
- **卡名→id 反查**：由 `self.engine.catalog.cards` 懒建 `{(card.kind, card.name): card_id}`。已实测：**同 kind 内重名组数 = 0**，反查唯一；若未来出现重名，`_card_index` 取首个并在账本记 `name_ambiguous += 1`，A-33 J6 要求该计数为 0（防止悄悄退化成纯文字）。
- **尺寸**：`_card_face_size()` = 240×336 @96dpi，与 A-19/20/21 的卡牌期望同源；比例 5:7，绑定层 `_fit_size` 等比缩放不会拉伸。
- **布局**：标题 → 卡面 Label（固定尺寸）→ 正文（`wraplength=420`，可滚动）→ 确定按钮。窗口 `resizable(False, False)`，不改变任何既有窗口尺寸断言。
- **缺图兜底**：`photo is None` → 退回 `_InfoDialog` 纯文本；账本留 `surface="card"`、`photo=None` 记录 → A-33 J2 直接 FAIL（fail-closed，不允许"看起来还行"就通过）。

### 4.2 六条机读判据

> 完整可抄文本见 `.codebuddy/wfat/art_acceptance_criteria.md` §2。此处给设计与理由。

| 编号 | 判据 | 机读方式 | 阈值 |
| --- | --- | --- | --- |
| **J1** | 棋盘已放置房间全部有图 | 驱动本地对局 → `len(state.board)` vs `board.canvas_image_items` | `rooms_placed ≥ 8` 且 `turns_played ≥ 6` 且 `canvas_image_items ≥ rooms_placed` 且 `rooms_with_image == rooms_placed` |

| **J3** | 全账本零占位 | 遍历 `ledger` | `len(ledger) ≥ 20`；`placeholder==true` 计数 **= 0**；无路径含 `assets/placeholders/` 或 `assets_ww/`；每条 `record_id` 在 P 表中 `availability=usable`、`runtime_status=ok` |
| **J4** | 玩家头像覆盖 | `surface=="portrait"` 记录 vs 本局玩家 | 覆盖全部 N 名玩家；`record_id` 落在 12 位 character 内且互不重复；尺寸 64/160 档 ±2 |

| **J6** | 取图键可反查 + 不可达位显式化 | 对账本每条 `key` 调 `registry.resolve` | 解析失败 0；`record_id` 一致；`name_ambiguous == 0`；`unreachable == ["storeroom"]`（唯一允许项） |

**J1 为什么要求 `rooms_placed ≥ 8`**：开局即放置 5 间起始房（`engine.py:485-492`）。若只要求"图数 ≥ 房间数"，一个只画起始房的实现也能过。要求 ≥8 强制发生至少 3 次探索，覆盖"新房间在同一帧拿到图"这条真实风险路径。

**J3 为什么是唯一硬兜底**：`load_asset_photo` 在文件缺失时返回**占位图而不是 None**，所以"没报错"不等于"用了真图"。J3 直接对账本判占位，把这条歧义钉死；J1/J2/J4/J5 只在各自 surface 上判"有没有画"，J3 判"画的是不是真图"。

**J6 为什么值得单列**：三处 surface 用 `runtime_key`，W-3 用 `content_ref`/裸 id。键口径一旦错，图片会静默落到"解析失败"分支，J1 只看到"图少了"，定位成本高。J6 把"键能不能反查"与"哪一位结构性不可达"变成可读结论。

## 5. 回归与再认证计划

### 5.1 `ui.py` 变更会触发什么（精确链条）

先说清两层"冻结"语义，避免用错证据：

| 层 | 载体 | 内容 | `ui.py` 是否在内 |
| --- | --- | --- | --- |
| (a) 报告冻结哈希表 | `run_p_table_execution.py:440-454` `FROZEN_FILES`（13 项） | 本轮生成时**重算**并与当前文件比对 | **否** |
| (b) claim 失效清单 | 报告 `invalidates_on` / `run3_completion_criteria.md` §3.5 | 任一关键产物变化即 claim 失效 | **是** |

因此：**A-01 的机读判定不会因 `ui.py` 漂移而 FAIL**（A-01 断言的是"同一轮内哈希自洽"，不是"跨轮冻结"）；但按 (b)，`ui.py` 变更使 `completion_claim@execution=attested` **立即失效**。真正会在机读上翻车的项是：

| 项 | 触发条件 | 变更后状态 |
| --- | --- | --- |
| A-19 / A-20 / A-21 | 独立验收 `_fresh_enough(ui_capture, [ui.py, ui_asset_binding.py, p_table])`：`ui_capture.json` mtime < `ui.py` mtime | **FAIL**（不是 NOT_RUN） |
| A-22 | 不校验新鲜度，读 100% 档对比度值 | 数值不变则仍 PASS，但证据已不代表当前代码 |
| A-03 / A-13 / A-14 / A-15 | `_verify_fresh_stale()`：`p_table_verify_final.json` 早于 `ui.py` | **NOT_RUN** |
| A-24 | 执行器 A-19…A-21 只读 `ui_data`，不校验新鲜度 → 仍 PASS；独立验收 FAIL | **口径冲突 → not-attested** |
| A-01 | 本轮重算，自洽 | 仍 PASS（不代表 claim 有效） |
| A-12 | 新增用例 | 63 → ≥69（只允许增加） |
| A-11 | 契约 32 项复跑 | 预期仍 32/32，需实证 |
| A-18 | 新增常驻图片（估算 <10 MB） | 峰值 68 MiB → 预计 <100 MiB，远低于 1536 MiB |
| A-26 | 两轮背靠背 | 必须重跑两轮 |
| A-28 | 签发 | 必须重签 |

> **关键推论**：不能靠"三档数字没变"跳过重拍。执行器不校验新鲜度、独立验收校验——两边不一致会落到 A-24，照样 not-attested。**必须重拍，且重拍后数值应与基线逐档相等**（见 §5.2）。

### 5.2 三档 DPI 证据：为什么数值不受影响

五条不变量（缺一条就得重议，而不是重拍）：

| # | 不变量 | 现状锚点 | 本次是否触碰 |
| --- | --- | --- | --- |
| I-1 | 预览页缩放公式与基准不变 | `_art_scaled_size` / `ART_ROOM_BASE=(128,128)` / `ART_CARD_BASE=(240,336)` / `ART_DPI_OVERRIDE` | 否 |
| I-2 | `dialog._art_photo` 属性名与语义不变 | `qa/ui_capture.py:307,325` | 否（新增用 `_art_refs`，不复用该名） |
| I-3 | 帮助窗口几何不变 | `plan["geometry"]`，三档窗口 1000×760 / 1250×950 / 1500×1140 | 否（新缩略图只进 `_InfoDialog`/`_PlayerDetailDialog`/tooltip/棋盘） |
| I-4 | 卡面尺寸只有一套公式 | 预览页 240×336 基准 | 否（对局卡面复用同一 `240×336` 基准） |
| I-5 | DPI 感知与读取路径不变 | `_configure_windows_dpi_awareness()` / `_read_effective_dpi()` | 否 |

推论：重拍三档后，`room_physical` 应为 128/160/192，`card_physical` 应为 240×336 / 300×420 / 360×504，`window_size` 三档不变，比值 5:7 不变。**"不受影响"是可验证命题，不是声明**——把它写成回归比对项：

> R-DPI：重拍后 `qa/ui_capture.json` 与基线（`p-table-final-20261121T194105` 随附的 `ui_capture.json`）逐档比较 `room_physical`、`card_physical`、`window_size`、`contrast_*`，必须完全相等；任一不等即视为"本次变更影响了 DPI 口径"，需先修正代码再重拍，不得直接改期望值。

### 5.3 再认证步骤（命令级）

顺序不可交换（写进程必须先停，验收必须最后跑）：

| 步 | 动作 | 产出 | 通过标准 |
| --- | --- | --- | --- |
| R1 | 实现四处接线 + 新增探针/用例/A-33 | 代码 | 本地自测通过；`python -m py_compile` 通过 |
| R2 | 跑独立探针 | `qa/game_art_probe.json` + `qa/screenshots/art_*.png` | `verdict=PASS`；`counters.placeholder_hits=0` |

| R4 | 第一轮收口 | `reports/p_table_execution_final.json`（R1 轮） | A 表含 A-33 |
| R5 | 停止所有写进程，第二轮收口（同解释器、同产物、无写进程） | 第二份报告 | A-26 `identical=true`，`diffs=[]` |

### 5.4 失效条件（新增）

现有失效清单（`invalidates_on`）已含 `ui.py`。本次追加：

1. `qa/game_art_probe.json` 缺失 / `mode != real-tk` / `inputs.*_sha256` 与当轮产物不一致 → A-33 NOT_RUN，claim 上限 partial。
2. `qa/screenshots/art_*.png` 任一缺失或非 PNG → A-33 FAIL（不得用"截图丢了但断言过了"解释）。
3. `game_art_probe.py` 采集器版本变化而证据未重采 → A-33 失效。
4. P 表新增/删除行导致 `record_id` 集合变化 → A-33 与 A-30 同时失效（本轮 P 表零变更，故不触发）。

## 7. 风险与回滚

| 风险 | 触发条件 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 图片引用被 GC → 瓦片/头像变空白 | 只依赖 LRU 缓存持图，缓存淘汰即回收 | 视觉事故，且 A-33 可能漏判（账本仍记录成功） | §3.1 契约 5：显示引用与缓存分离；T-06 用例 6 断言 |
| 首帧解码卡顿 | 一次重绘 25~50 张 512² PNG | 开局白屏 0.5~2s | 尺寸阶梯 + 缓存；`redraw_ms` 作为非阻断观测入探针 |
| 房间图压过房名导致不可读 | 图铺满瓦片 | 可读性下降（A-22 不断言对局区） | 底部实心名称带（`panel3`）+ 图只占上部 `ts-band_h` |
| 卡名反查失配 → 静默退化为纯文字 | 未来新增同名卡 | A-33 J2 失败但定位困难 | `name_ambiguous` 计数入探针；J6 要求 =0 |
| 三档 DPI 证据被顺手改期望值 | 重拍后数值不等 | 削弱 A-19/20/21 | §5.2 R-DPI 回归比对；不许改期望值 |
| 探针在验收期间运行 | 写入 `qa/` 触发 A-03 | 整轮 not-attested | §4.4 证据纪律 2：探针先跑完 |

**回滚**：`ui.py` 四处接线可按 W-1…W-4 独立回退（共用入口可保留，仅停用调用点，账本会自然空转）。回退后必须重跑 §5.3 全流程——因为 `ui.py` 再次变化，A-19/20/21 证据再次过期。
